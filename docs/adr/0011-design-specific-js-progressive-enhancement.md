# 设计专属 JavaScript：仅作渐进增强，不建立共享视觉运行时

## 背景与决定

纯 CSS 足以完成大量拟物构图，但跨页手帐、地图探索与角色登场等“交互参与叙事”的表达，可能无法仅靠 CSS 达成。为避免所有设计被迫接受同一交互引擎，也避免脚本成为内容可达性的前提，决定：

1. 只有某套设计隐喻的核心交互在纯 CSS 下存在具体表达缺口时，才允许引入 **Design-specific interaction**；不得仅为了增加动画、装饰或“看起来更高级”而写脚本。
2. 脚本属于单个设计目录，只在该设计页面加载；不得建立跨设计共享的视觉交互运行时，不得为少量功能新增前端框架，也不得引入第三方交互依赖。
3. 每套设计最多一个客户端入口，压缩后主题脚本不超过 **12KB gzip**。禁止滚动劫持、以自定义光标替代系统光标、Canvas-only 文本、WebGL、自动播放声音和主题级无限循环；`requestAnimationFrame` 只在实际交互期间运行。
4. 脚本必须渐进增强。无 JavaScript、模块加载失败、初始化抛错或减动态设置下，核心资料、非空可选区块和真实链接仍须完整可见、可导航。隐藏或重排内容的设计级门控只能在初始化成功后开启；失败路径必须恢复静态终态。
5. 功能交互不能只支持指针；键盘操作、焦点归还、可见焦点与语义状态必须成立。减动态可以取消编排动画，但不得取消访问内容所必需的交互能力。
6. 切换页 `Preview.astro` 永远不执行设计脚本；共享 `Reveal` 与 `ContextMenu` 保持现有职责，不并入设计脚本。

## 被否决的选项

- **六套设计一律加入 JS**：把技术存在感误当成设计差异，增加降级、无障碍与维护成本。
- **建立统一可爱交互引擎**：六套隐喻彼此独立，统一状态机与视觉参数会制造不必要耦合。
- **用 JS 作为页面内容入口**：脚本失败会直接摧毁资料页，违反项目内容默认可见契约。
- **继续绝对禁止设计页 JS**：会让确有必要的空间探索与编排式登场只能退化为静态示意。

## 后果

- 本决定修订 ADR 0003 决定 4 中适用于设计页的部分；共享菜单与 Reveal 的既有决策不变。
- 各设计须在 `DESIGN.md` 写清脚本存在理由、交互状态、键盘路径、无 JS 终态、减动态行为、体积预算与停止条件。
- 验证必须覆盖脚本成功、脚本失败与无 JS 三种路径；`design-page-verify` 的现有降级矩阵据此扩展。
